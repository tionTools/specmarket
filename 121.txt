Context
Patch 120 fixed the Edge gateway rejection for scheduled NovaPay requests.
Controlled scheduled invocation request 12582 then reached novapay-data successfully, but pg_net recorded:
- timed_out = true
- timeout = 5000 ms
- status_code = null
- content = null
The same invocation nevertheless completed inside novapay-data and updated bank_account_cache:
- request created: 2026-09-19 13:57:11 UTC
- novapay cache updated_at: 2026-09-19 13:57:22.632 UTC

Therefore the remaining issue is not NovaPay auth, cron, or the Edge Function. pg_net stops waiting after its current 5-second timeout before novapay-data normally finishes.

Goal
Make the scheduled HTTP request wait long enough to capture the actual Edge Function response instead of storing a false timeout.

Implementation
Add one new migration:
- supabase/migrations/20260919160000_novapay_sync_http_timeout.sql

The migration must replace only public.invoke_crm_novapay_sync() with the same current implementation plus:
  timeout_milliseconds := 180000

Why 180000
Supabase Edge Functions have a 150-second request idle timeout. A 180-second pg_net timeout intentionally exceeds that gateway limit, so pg_net should receive either the real function response or the platform's terminal HTTP error instead of timing out first.
This is a low-frequency job (every 15 minutes during the daytime window), so the longer per-request timeout does not create meaningful request pressure.
