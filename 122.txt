Context / regression
The NovaPay statement currently assigns the same day-closing balance to every incoming payment of the same day.

Current wrong behavior on 19.09.2026:
- 13:56:25 +125.37 -> 8000.43  (WRONG)
- 19:47:04 +626.85 -> 8000.43  (latest row is correct)

Expected running balances:
- previous day 18.09 closing / latest receipt balance: 7248.21
- 19.09 13:56:25 +125.37 -> 7373.58
- 19.09 19:47:04 +626.85 -> 8000.43

Math:
7248.21 + 125.37 = 7373.58
7373.58 + 626.85 = 8000.43

Root cause
Patch 115 restored balances by mapping each receipt to one daily close:
  balance: dailyBalances.get(paymentDate)

Patch 116 then overrides today's daily close with current available balance:
  dailyBalances.set(dateTo, available)

Therefore all same-day receipts get the same final/current balance.

Goal
Keep the existing daily closing balance source, but reconstruct the balance of each displayed incoming receipt within a day.

Algorithm
Input receipts are already sorted newest-first.
For each calendar date independently:
- newest incoming receipt gets the daily closing balance;
- moving backwards in time, subtract the amounts of later incoming receipts;
- use integer cents for arithmetic to avoid floating-point rounding drift.

For the exact production regression:
- daily close = 8000.43
- newest +626.85 => 8000.43
- earlier +125.37 => 8000.43 - 626.85 = 7373.58

The updated-payments path must reuse balances already calculated from the full statement by provider ID/UETR alias. Do not independently recalculate from the partial updated subset.

Implementation notes
1. extractReceipt() no longer assigns a day close directly. It starts with balance: null.
2. Full statement incoming receipts are sorted newest-first, then passed to:
   assignIncomingBalancesFromDailyClose(receipts, dailyBalances)
3. The helper reconstructs balances by day using integer cents.
4. Updated-payment receipts reuse the balance from the full statement by provider alias via:
   copyKnownBalancesByProviderAlias(...)
5. The helper must not mutate the original receipt objects.
6. Preserve all existing receipt/event dedupe logic.
