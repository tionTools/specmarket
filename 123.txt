IMPORTANT
Patch 122 is BLOCKED and MUST NOT be applied.
Patch 123 supersedes Patch 122 completely.

Why Patch 122 was rejected
Patch 122 reconstructed earlier balances by subtracting only later incoming receipts.
That is mathematically wrong when a debit/outgoing movement occurs between incoming receipts.

Counterexample:
- opening 1000
- 10:00 +100 => real 1100
- 11:00 -50 => real 1050
- 12:00 +200 => closing 1250

Subtracting only later credits would incorrectly produce 1050 for the 10:00 receipt.
Correct reverse reconstruction must include every balance-affecting debit and credit.

Official NovaPay data available
GetAccountExtract provides daily aggregates:
- InCome
- DebitAmount
- CreditAmount
- OutCome
and each payment is represented by Docs.

Current GetPaymentsList(date_type=0) already returns the conducted statement payments used by novapay-data, including debit and credit account fields and Amount.

Goal
Restore exact balance-after-payment for displayed incoming NovaPay receipts without inventing values.

Correct algorithm
For each calendar day:

1. Get daily summary from GetAccountExtract:
   opening = InCome
   debitTotal = DebitAmount
   creditTotal = CreditAmount
   closing = OutCome

2. For today only, preserve current behavior:
   closing is overridden by fresh GetAccountRest.available_balance.

3. Take ALL conducted documents from statement GetPaymentsList(date_type=0), not only incoming receipts.

4. Classify each movement by account IBAN:
   - credit: CreditCodeIBAN == account IBAN and DebitCodeIBAN != account IBAN
   - debit: DebitCodeIBAN == account IBAN and CreditCodeIBAN != account IBAN
   - otherwise unknown

5. Require every movement to have:
   - calendar date
   - valid Changed, fallback Created datetime
   - positive amount
   - known credit/debit direction

6. Validate the daily summary itself:
   opening + creditTotal - debitTotal == closing

7. Validate completeness of GetPaymentsList against GetAccountExtract:
   sum(all credit movements) == creditTotal
   sum(all debit movements) == debitTotal

If these checks do not match, DO NOT calculate any historical balance for that day.
Leave balance null instead of returning a plausible but false number.

8. Require deterministic ordering.
If two account movements have the exact same timestamp, do not invent an order.
Leave balances null for that day.

9. For a validated day, start from closing and walk all movements newest -> oldest:
   - balance after current movement = current running balance
   - reverse credit +A by subtracting A
   - reverse debit -A by adding A

10. Only displayed incoming receipts receive the resulting balance, matched by provider ID/UETR alias.

11. Updated-payments path must NOT independently recalculate from its partial subset.
It reuses balances calculated from the full statement by provider alias.

- parseExtractDayBalances is replaced by parseExtractDaySummaries.
- Summary fields:
  opening
  debitTotal
  creditTotal
  closing
- extractReceipt no longer blindly injects one day-close balance.
- extractBalanceMovement builds a movement from every conducted statement document.
- The helper uses integer cents for all balance math.
- A daily aggregate mismatch, invalid movement, missing timestamp, unknown direction, or same-timestamp ambiguity suppresses calculated balances for that day instead of fabricating them.
- Current top-level NovaPay account balance remains GetAccountRest.available_balance.
- Today's summary closing remains overridden with available_balance exactly as before.
- No new API call is added.
