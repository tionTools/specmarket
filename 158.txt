Суть (строго по текущему коду):
- Ранее sync-delivery-tracking делал отдельный SELECT crm_orders.delivery для каждой проверенной ТТН после ответа перевозчика и повторный SELECT в catch.
- Теперь ответы перевозчиков собираются группами по 25, актуальные delivery для этих заказов читаются одним SELECT crm_orders(id,delivery).in(id, ids) на группу. Перед обновлением ОБЯЗАТЕЛЬНО сохраняется sameShipment(original, current). Не изменять это условие.
- Если пакетное чтение падает, выполняется fallback по одному заказу. Если текущее состояние отсутствует или изменилась ТТН/перевозчик — результат API не записывать.
- Существующее пакетное сохранение crm_delivery_tracking_state по 25 сохранено. Для изменившихся доставок UPDATE crm_orders остаётся по одному; не заменять его слепым массовым upsert, который затрёт другие поля/параллельные изменения.
- Дневные/ночные интервалы, механика marketplace cron, API площадок, Android, напоминания 157 не меняются. SQL-миграций нет. Это первый измеримый шаг глубокой оптимизации, не обещать заранее процент общего снижения.
- Добавлены изолированные Deno-тесты пакетного чтения, fallback, пропавшего заказа, пустой очереди и thrown error.
