# Production logging: minimal profile for SpecMarket

The CRM does not depend on keeping routine Supabase Logs Explorer events.
Platform API gateway and Edge Function invocation events are generated by Supabase and cannot be disabled by removing application `console` calls.

## Project-level settings (run once with authorized Supabase CLI)

Do not run these commands against a local database or another Supabase project. Inspect the target project and its current configuration first. Supabase's official CLI supports `cron.log_statement`, `log_connections`, and `log_disconnections`:

```sh
supabase postgres-config update --project-ref rtkhgldaswsclkorlyxx --experimental \
  --config cron.log_statement=false \
  --config log_connections=false \
  --config log_disconnections=false
```

`cron.log_statement=false` requires a PostgreSQL restart; schedule that small interruption rather than assuming zero downtime. Do not use `--replace-existing-overrides`.

Inspect project-specific SQL statement logging in Supabase SQL Editor before changing it:

```sql
select name, setting, source, context, pending_restart
from pg_settings
where name in (
  'log_statement', 'log_min_duration_statement', 'log_duration',
  'log_connections', 'log_disconnections', 'cron.log_statement',
  'pgaudit.log'
)
order by name;
```

For the role executing your SQL operations (usually `postgres`), disable explicit statement logging if it is active:

```sql
alter role postgres set log_statement to 'none';
alter role postgres set log_min_duration_statement to '-1';
alter role postgres set log_duration to 'off';
```

Role-level settings take effect for *new* sessions. Do not change `log_min_messages`, `log_min_error_statement`, Postgres crash/error events or security/audit settings blindly. Do not enable `cron.log_run=false` using unsupported CLI parameters: that setting controls the separate cron run-history table, not the hosted Logs Ingest stream.

After applying, only verify the settings themselves (`pg_settings`/`pg_roles`) and that existing scheduled functions still execute. No recurring daily Logs Explorer review is required. The NovaPay failure journal is retained because the CRM displays those failures; successful entries are already deleted.
