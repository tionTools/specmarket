Purpose
Stop depending on GetAccountExtract opening/closing for per-payment balances.
The current account balance is already authoritative and available as GetAccountRest.available_balance.
The 7-day GetPaymentsList already supplies all conducted movements needed to reconstruct balances for rows inside that same window.

Algorithm
Start from current account balance and walk all valid account movements backwards in time:
- current balance = balance after the newest movement;
- newest credit: store current balance for that receipt, then subtract its amount;
- newest debit: add its amount back;
- continue backwards.

For production:
current = 8000.43
reverse +626.85 => that receipt balance 8000.43; previous running 7373.58
reverse +125.37 => that receipt balance 7373.58; previous running 7248.21
reverse +1248.72 => that receipt balance 7248.21

This uses ALL valid credit/debit movements, including debits not displayed in the incoming-only table.

Matching
Prefer provider ID/UETR aliases.
If NovaPay does not expose an alias for a receipt, fallback match uses:
- legacyDate
- occurredAt
- amount
This prevents a valid receipt from staying null only because ID/UETR is absent.

Scope
Exactly:
- supabase/functions/novapay-data/index.ts

- supabase/functions/_shared/novapay-running-balance_test.ts

Do not touch auth, cron, locks, Vault, dedupe, email, schema/migrations, Monobank, marketplaces, Android.

Important
No diagnostics patch.
No GetAccountExtract-derived per-row math.
No daily opening/closing is required by assignRunningBalances after this patch.
The existing GetAccountExtract call is left in place for minimal scope, but it no longer controls row balances.
