Context
The visible NovaPay statement already has per-document time values used for the rows:
- 19.09.2026 13:56:25
- 19.09.2026 19:47:04

The bug is simple:
the current code assigns one end-of-day balance to every payment of the same day.

Expected 19.09 math:
opening 7248.21
13:56:25 +125.37 = 7373.58
19:47:04 +626.85 = 8000.43

Previous one-payment days looked correct only because a single payment's running balance equals the day closing balance.

Goal
Implement the running balance exactly like a spreadsheet:
- start from the day's opening balance (InCome);
- sort ALL conducted account movements by the same occurredAt timestamp already used for statement rows;
- credit => add Amount;
- debit => subtract Amount;
- after each incoming payment, store the current running balance for that payment;
- at the end, the calculated balance must equal the day closing balance;
- if it does not match, leave balances for that day null instead of inventing values.

Current day
GetAccountExtract may not provide current OutCome.
Preserve existing behavior:
- opening comes from GetAccountExtract InCome;
- today's closing is overridden by GetAccountRest.available_balance.

No reverse reconstruction.
No Created-vs-Changed ordering proof.
No new API calls.
No schema changes.

Timestamp
Use the exact same event timestamp logic already used by receipt rows:
- Changed when valid;
- fallback Created.
The balance calculation and displayed row therefore use the same occurredAt value.
