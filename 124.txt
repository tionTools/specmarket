Official NovaPay facts used by the algorithm
GetAccountExtract day summary provides:
- InCome = opening balance
- DebitAmount = total debits/write-offs
- CreditAmount = total credits/incoming
- OutCome = closing balance

GetPaymentsList provides conducted payment documents with:
- ID for conducted payments
- DayDate = posting date
- DebitCodeIBAN / CreditCodeIBAN
- Amount
- Created
- Changed
- UETR when available

Changed is documented as last-change datetime; Created is creation datetime. Neither is documented as a formal account-ledger sequence number.

Therefore Patch 124 does NOT blindly trust one timestamp. It calculates a day only when Created and Changed independently imply the same strict ordering of all account movements.

Correctness algorithm

1. GetAccountExtract is parsed into day summaries:
   opening / debitTotal / creditTotal / closing.

2. Missing or invalid aggregate values remain null.
   IMPORTANT: null / undefined / blank strings MUST NOT become numeric zero.

3. Today's closing balance is still overridden by the fresh
   GetAccountRest.available_balance, preserving existing behavior.

4. Use ALL conducted statement GetPaymentsList(date_type=0) documents for balance math:
   not only incoming/displayed receipts.

5. Classify every conducted document:
   credit when CreditCodeIBAN == account IBAN and DebitCodeIBAN != account IBAN;
   debit when DebitCodeIBAN == account IBAN and CreditCodeIBAN != account IBAN;
   otherwise unknown.

6. Every movement must have:
   - a date;
   - a positive amount;
   - known direction;
   - valid Created datetime;
   - valid Changed datetime.

7. Validate the daily aggregate identity:
   opening + creditTotal - debitTotal == closing
   using integer cents.

8. Validate movement completeness:
   sum(all credit movements) == CreditAmount
   sum(all debit movements) == DebitAmount

9. Validate ordering:
   - Changed timestamps are unique;
   - Created timestamps are unique;
   - sorting all movements by Changed gives exactly the same movement order as sorting by Created.

If the two documented timestamps disagree on movement order, Patch 124 refuses to invent a balance for that day.

10. For a fully validated day:
    start from closing and reverse every movement newest -> oldest:
    - credit +A: balance after it is current running balance; reverse by subtracting A;
    - debit -A: reverse by adding A.

11. After reverse traversal, the reconstructed balance must equal opening.
    Otherwise discard all calculated balances for that day.

12. Only incoming/displayed receipts receive the calculated balance, matched by provider ID/UETR alias.

13. The partial updated-payments path does not calculate balances independently.
    It reuses balances from the validated full statement by provider alias.

Fail-safe rule
If completeness, aggregate identity, timestamp validity, timestamp uniqueness, timestamp-order agreement, movement direction, or final opening-balance check fails:
- balance stays null for that day.
- NEVER fall back to one day-close value for every same-day receipt.
- NEVER guess.
