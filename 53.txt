3. Marketplace accept backend
Расширь текущие Edge Functions так, чтобы Android мог реально принимать новый заказ на всех трёх площадках.

Prom:
- не переписывай рабочую Patch52-логику без необходимости;
- сохрани idempotency, processed_ids confirmation, optimistic concurrency guard и `completeExternalIds`.

Epicentr:
- добавь отдельный request action (предпочтительно `acceptExternalIds`, если это не конфликтует с текущим contract);
- cron/scheduled и guest запрещены;
- строгая нормализация IDs, dedupe, max 100;
- load CRM row только `platform='Эпицентр'`;
- new/accepted/final classification должна отражать текущий sync mapping;
- перед transition проверь allowed statuses через официальный API, если контракт это позволяет;
- выполни реальный seller-confirmation transition;
- только после подтверждения площадки обнови CRM;
- CRM update защищён старым `status` + `updated_at`/эквивалентным optimistic concurrency условием;
- already accepted — idempotent result без регресса;
- external failure => CRM не меняется;
- concurrent conflict => понятный 409 и refresh path.

Kasta:
- аналогичный dedicated accept action в `sync-kasta-orders`;
- точный API write path только после проверки official HUB docs;
- `Created` / реальный CRM `Новый` -> marketplace `ConfirmedBySupplier`;
- после подтверждения площадки CRM становится текущим accepted status (`Принято`), не раньше;
- те же auth/idempotency/concurrency/failure guarantees.

Вынеси pure/helpers там, где это уменьшает дублирование и делает Deno tests реальными, но не устраивай большой рефакторинг unrelated sync logic.

4. Android acceptance
В Patch52 `canAccept` жёстко Prom-only. Переделай на platform-aware eligibility/routing:
- Prom + new -> `sync-prom-orders`;
- Epicentr + new -> `sync-epicentr-orders`;
- Kasta + new -> `sync-kasta-orders`;
- guest/unauth/malformed external ID/final/accepted/cancelled/returned -> no action.

Используй общий UX:
- кнопка `Принять` в details;
- AlertDialog с площадкой и № заказа;
- защита от двойного нажатия;
- нормальные сообщения success/already accepted/409/API failure;
- после любого ответа адресный refresh заказа;
- Realtime остаётся дополнительным общим обновлением, но не единственным источником проверки результата.

5. Push notifications — архитектура
Нужны реальные background/killed-app notifications, поэтому использовать FCM, а не бесконечный polling или только Realtime.

Сначала проверь, существует ли уже Firebase project/public Android config и server credential в окружении/секретах. Ничего секретного не печатай в логи.

Если Firebase-конфигурации нет:
- не создавай самовольно внешний Firebase project;
- не придумывай фейковые значения;
- можешь подготовить безопасный код/migration/tests, но до финального `commit/push/deploy` не объявляй задачу завершённой;
- в отчёте перечисли ровно какие public Android Firebase values/config и какие Supabase secret values нужны для продолжения.

Если конфигурация есть, реализуй полностью.

7. Durable new-order notification event
Нельзя посылать push на любой UPDATE `crm_orders`.

Сделай idempotent outbox/event model:
- unique `(order_id, event_type)` или эквивалент;
- событие `new_order` создаётся только когда normal sync реально создаёт новый текущий Prom/Epicentr/Kasta заказ;
- update existing order, retry/realtime/status sync не создают новый event;
- full historical/backfill не создаёт шторм старых notifications;
- transient sender failure можно retry;
- permanent invalid token выключается/удаляется;
- push failure никогда не откатывает order sync.

Выбери реализацию, которая соответствует уже существующим `pg_cron`/Edge Function patterns проекта. Не добавляй dashboard-only автоматику, которую нельзя воспроизвести из repo migrations/config.

8. FCM sender
Используй текущий рекомендованный FCM HTTP v1/server mechanism.
- service account/private key только в Supabase secret/runtime;
- никаких server credentials в git/Android/web/GitHub Actions output;
- payload: platform, display/order number, internal order id; без customer phone/address/payment private details;
- invalid registration token обрабатывается;
- delivery event marked sent только после реального success;
- sender failure логируется безопасно без sensitive payload.

Если нужен новый Edge Function sender — добавь его, Deno tests и deployment step.

9. Android FCM
- подключи только стабильные совместимые Firebase Android dependencies;
- получить/refresh FCM token;
- upsert device registration after authenticated session;
- Android 13+ notification permission;
- Settings switch `Уведомления на этом устройстве` действительно меняет server routing;
- одна и та же учётка на двух телефонах имеет независимые switches;
- logout disable/unregister local device;
- foreground notification не дублируется нелепо;
- tap по notification открывает нужный order detail после session restore; если нужна login — сохранить безопасный pending internal order id и открыть после login.

Не логируй tokens/customer data.
