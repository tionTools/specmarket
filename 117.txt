Goal
Find and fix the reproducible NovaPay JWT rotation failure. Patch 117 is a CANDIDATE fix, not an assumption.

Observed facts
1. Production authenticates successfully with a fresh UI-generated refresh_token/public_certificate pair.
2. NovaPay returns a new refresh_token/public_certificate pair.
3. Production saves that returned pair; logged response fingerprints equal logged stored fingerprints.
4. If JWT/expiry are cleared immediately after that successful production rotation, the very next production UserAuthenticationJWT using the returned pair fails with:
   logic_error — Access Denied! Refresh token does not apply to login
5. Independent PowerShell SOAP/XML tests do NOT reproduce this:
   - returned pair works on the next call;
   - a returned pair also worked after ~596 minutes.
6. Therefore this is not explained by a normal ~2h JWT expiry or by NovaPay automatically expiring the returned pair.
7. The failure is specific to the production auth path or to how production handles the returned credentials/request.

IMPORTANT — independent Astra diagnosis first
Do NOT assume the XML entity-decoding hypothesis is correct.
Before applying 117.patch, independently trace the NovaPay auth path in the narrow scope below and determine the strongest concrete explanation for why a pair returned by NovaPay can be logged/saved by production yet immediately fail when production sends it back.

Candidate hypothesis in 117.patch
Production uses fast-xml-parser@5.11.1 for UserAuthenticationJWT. PowerShell uses .NET [xml].
The candidate patch enables entity decoding for UserAuthenticationJWT responses because PEM line breaks or other characters may be represented by XML character references.
This is only a hypothesis. Confirm it from code/parser behavior if possible; reject it if the evidence contradicts it.
