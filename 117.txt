Goal
Fix the reproducible NovaPay JWT rotation failure where:
1. production successfully authenticates with a fresh UI-generated refresh_token/public_certificate pair;
2. NovaPay returns a new refresh_token/public_certificate pair;
3. production stores that returned pair and stored fingerprints match response fingerprints;
4. after forcing JWT renewal immediately, NovaPay rejects the stored returned pair with:
   logic_error — Access Denied! Refresh token does not apply to login
5. the independent PowerShell XML client can use a NovaPay-returned pair successfully even after ~596 minutes.

Working hypothesis
Production parses UserAuthenticationJWT SOAP XML with fast-xml-parser@5.11.1. The current parser does not enable htmlEntities. NovaPay/WCF may encode PEM line breaks as numeric XML character references. If those references remain literal text, response/stored fingerprints still match each other, but the persisted certificate is not the certificate NovaPay issued. PowerShell [xml] decodes XML character references, matching the observed difference.

Patch 117 changes only the parser used for UserAuthenticationJWT responses in:
- supabase/functions/novapay-data/index.ts
- supabase/functions/novapay-balance/index.ts

It leaves all other NovaPay XML parsing unchanged.
